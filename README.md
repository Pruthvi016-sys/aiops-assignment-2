## Question 1 — Naive vs. Multi-Stage Docker Build

**Folder:** `q1/`

| File | Description |
|---|---|
| `Dockerfile.naive` | Single-stage build — installs deps, copies everything, trains the model, all in one final image. |
| `Dockerfile.multistage` | Two-stage build — trains the model in a `python:3.11` builder stage, copies only the venv + `model.joblib` + `app.py` into a slim `python:3.11-slim` runtime stage. |
| `app.py` | FastAPI app exposing `POST /predict` and `GET /healthz`. |
| `data_gen.py` | Generates the deterministic 1,000-row synthetic spam/ham dataset. |
| `train_model.py` | Trains the `TfidfVectorizer` + `MultinomialNB` pipeline, saves `model.joblib`. |
| `requirements.txt` | Python dependencies. |
| `evidence/` | Screenshots of both builds, `docker images` size comparison, and `/predict` + `/healthz` test output. |

**Result:** multi-stage image content size (~176MB) vs. naive image content size (~534MB) — roughly a 3x reduction, since the builder stage's compiler toolchain, pip caches, and training scripts never make it into the final image.

**To reproduce:**
```bash
cd q1

# Naive build
cd ~/q1
docker build -t q1-api-naive -f Dockerfile.naive .
docker images q1-api-naive
docker run -d -p 8000:8000 --name q1-api-naive-c q1-api-naive
sleep 3
docker ps
curl -s http://localhost:8000/healthz
curl -s -X POST http://localhost:8000/predict -H "Content-Type: application/json" -d '{"text": "WIN a FREE iPhone now! Click here: bit.ly/xyz123"}'
curl -s -X POST http://localhost:8000/predict -H "Content-Type: application/json" -d '{"text": "Hey, are we still meeting for lunch on Friday?"}'
docker stop q1-api-naive-c && docker rm q1-api-naive-c

# Multi-stage build
docker build -t q1-api-multistage -f Dockerfile.multistage .
docker images q1-api-multistage
docker run -d -p 8000:8000 --name q1-api-multistage-c q1-api-multistage
sleep 3
docker ps
curl -s http://localhost:8000/healthz
curl -s -X POST http://localhost:8000/predict -H "Content-Type: application/json" -d '{"text": "WIN a FREE iPhone now! Click here: bit.ly/xyz123"}'
curl -s -X POST http://localhost:8000/predict -H "Content-Type: application/json" -d '{"text": "Hey, are we still meeting for lunch on Friday?"}'
docker stop q1-api-multistage-c && docker rm q1-api-multistage-c

# Compare
docker images | grep q1-api

```

## Question 2 — Multi-Container Orchestration with Docker Compose

**Folder:** `q2/`

| File | Description |
|---|---|
| `app.py` | Same API as Q1, extended with a Redis cache check before each prediction (cache hit → return cached label; miss → predict, cache with a TTL, return). |
| `Dockerfile.multistage` | Reused from Q1 to build the `api` service's image. |
| `docker-compose.yml` | Defines two services — `api` (built locally) and `cache` (`redis:7-alpine`), connected via the default Compose network so `api` reaches Redis at hostname `cache`. |
| `data_gen.py`, `train_model.py`, `requirements.txt` | Same role as in Q1 (`requirements.txt` additionally includes `redis`). |
| `evidence/` | Screenshots of `docker compose up --build`, container health, and the cache-hit vs. cache-miss timing runs. |

**To reproduce:**
```bash
cd q2
docker compose up --build
```

In a second terminal, once you see `Uvicorn running on http://0.0.0.0:8000`:
```bash
# Confirm both containers are healthy
docker compose ps

# Confirm the api container can resolve/reach redis by service name
docker compose exec api python -c "import redis, os; r = redis.Redis(host=os.getenv('REDIS_HOST','cache'), port=6379); print(r.ping())"

# Cache-hit vs cache-miss timing evidence (first call = miss, rest = hits)
for i in $(seq 1 8); do curl -s -w "\nTime: %{time_total}s\n" -X POST http://localhost:8000/predict -H "Content-Type: application/json" -d '{"text": "WIN a FREE iPhone now! Click here: bit.ly/xyz123"}'; done
```

Expect the first response as `"cached":false` with a noticeably higher time, and every subsequent identical request as `"cached":true` with a consistently low time.

Tear down:
```bash
docker compose down -v
```

## Question 3 — Kubernetes Indexed Job: Parallel Data Validation

**Folder:** `q3/`

| File | Description |
|---|---|
| `Dockerfile.validator` | Minimal image that bundles the shard CSVs and `validate_shard.py`. |
| `generate_shards.py` | Generates 8 deterministic synthetic CSV shards (`shards/shard_0.csv` … `shard_7.csv`) with a known, seeded number of invalid rows per shard. |
| `validate_shard.py` | Runs inside each pod; reads `JOB_COMPLETION_INDEX` to pick its shard, validates rows (missing name/email/date, malformed email), prints a `RESULT_JSON:{...}` line. |
| `job.yaml` | Kubernetes Indexed Job — `completions: 8`, `parallelism: 8`, `completionMode: Indexed`, CPU requests = limits (`500m`), Downward API fields for pod name and node name. |
| `collect_results.py` | Uses the Kubernetes Python client to read every pod's logs via the API (not a shared volume) and aggregate the per-shard invalid-row counts. |
| `ground_truth.txt` | Expected invalid-row counts per shard, for self-verification. |
| `shards/` | The 8 generated CSV shards, baked into the validator image. |
| `evidence/` | Screenshots of cluster setup (kube-reserved trick), image load on both nodes, `kubectl get pods -o wide`, staggered start times, and `collect_results.py` output. |

**To reproduce** (assumes a 2-node minikube cluster; see the write-up for how the 4-CPU constraint was simulated):
```bash
cd q3

# Generate shards (only needed once, before the first image build)
python3 generate_shards.py

# Build and load the validator image onto BOTH nodes
docker build -t shard-validator:latest -f Dockerfile.validator .
minikube image load shard-validator:latest
minikube ssh --node minikube docker images | grep shard-validator
minikube ssh --node minikube-m02 docker images | grep shard-validator

# Run the Job
kubectl apply -f job.yaml
kubectl get pods -o wide

# Collect and verify results (requires: pip install kubernetes)
python3 collect_results.py
```

Clean up between runs:
```bash
kubectl delete job shard-validation-job --ignore-not-found
```

## Question 4 — Kubernetes Deployments: Self-Healing & Rolling Updates

**Folder:** `q4/`

| File | Description |
|---|---|
| `app.py` | The plain (non-cached) Q1 spam-detection API, with a `VERSION` string included in the `/healthz` response — used as the visible marker for the rolling-update test. |
| `Dockerfile.multistage`, `data_gen.py`, `train_model.py`, `requirements.txt` | Same role as in Q1. |
| `deployment.yaml` | 2-replica Deployment with CPU requests/limits and a `readinessProbe` against `/healthz`. |
| `service.yaml` | `ClusterIP` Service exposing the Deployment. |
| `evidence/` | Screenshots of the Deployment/Service coming up, the manual pod deletion + auto-recreation, and the `v1` → `v2` rollout with `rollout status`/`rollout history` output. |

**To reproduce:**
```bash
cd q4

# Build v1 and load onto both nodes
docker build -t spam-api:v1 -f Dockerfile.multistage .
minikube image load spam-api:v1

# Deploy
kubectl apply -f deployment.yaml
kubectl apply -f service.yaml
kubectl get pods -o wide
kubectl get deployment,svc spam-api
```

**Self-healing test:**
```bash
kubectl get pods -o wide
kubectl delete pod <one-spam-api-pod-name>
kubectl get pods -o wide -w   # watch a replacement pod get created automatically
```

**Rolling update test** — bump `VERSION` in `app.py` to `"v2"`, then:
```bash
docker build -t spam-api:v2 -f Dockerfile.multistage .
minikube image load spam-api:v2

kubectl set image deployment/spam-api spam-api=spam-api:v2
kubectl rollout status deployment/spam-api
kubectl rollout history deployment/spam-api
kubectl get pods -o wide   # confirm new pod names / new ReplicaSet hash
```

**Verify the live version:**
```bash
kubectl port-forward svc/spam-api 8080:80
```
In a second terminal:
```bash
curl http://localhost:8080/healthz
# Expect: {"status":"ok","version":"v2"}
```

## AI Usage Disclosure

Per assignment guidelines, AI tool usage is disclosed per question below. **Tool used: Claude (Anthropic).**

|---|---|
| **Report** | Used for LaTeX code and formatting to typeset the 2-page written report (structuring sections, tables, and code blocks within the page limit). |

| **Q2** | Used to understand `docker-compose.yml` syntax and service-networking conventions (service-name-as-hostname, `depends_on` health conditions), for writing and debugging the Redis-caching logic added to `app.py`, and for the exact `docker`/`docker compose` commands (`build`, `up --build`, `exec`, `ps`) used to verify the caching behavior. |
| **Q3** | Used to understand Kubernetes Job YAML syntax and fields (`completions`, `parallelism`, `completionMode: Indexed`, Downward API `fieldRef`s), for debugging the shard-validation script and Job manifest issues, and for the exact `kubectl` commands used to apply, inspect, and clean up the Job. |
| **Q4** | Used to understand Deployment/Service YAML syntax (`readinessProbe`, `resources`, label selectors), for the exact `kubectl` commands used to perform and verify the rolling update (`set image`, `rollout status`, `rollout history`), and for debugging issues encountered along the way (e.g. a rollout that silently no-op'd because the image tag update step was missed). |

**Overall impact:** Claude was used throughout mainly for correct YAML/Dockerfile syntax, exact command sequences, and debugging build/networking/scheduling issues as they came up, rather than for the underlying design decisions. The choice of parallelism and CPU sizing in Q3, the resource values and probe configuration in Q4, the interpretation of all terminal evidence, and the write-up's explanations were done manually. AI assistance had more impact on boilerplate, syntax reference, and troubleshooting than on the actual experimental/infrastructure design — most of the hands-on work (running the builds, applying manifests, reading and verifying evidence) was done by hand.
